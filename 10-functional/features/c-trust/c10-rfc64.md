# C10 — RFC draft (from #64)

**Status:** Draft · **Audience:** Operator · **Area:** C — Trust & correctness

---

> Scaffolded from RFC [#64](https://github.com/lemonfiber/spec/issues/64) on maintainer approval. This is a **Draft** —
> not binding, not citable — for a maintainer to refine into a proper feature
> before it is Accepted. The proposal is quoted verbatim below.

## Purpose

The problem this proposal addresses:

```text
lemonfiber proves the VPN isn't leaking and that hardlinks work at setup, but VPN configs drift, providers rotate keys, and volume mounts change after updates — so a stack that was proven correct can silently regress. There is no standing check that re-proves these properties over time.
```

## Behaviour

The proposed behaviour, as submitted:

```text
The tool SHOULD re-run the VPN egress proof and the hardlink inode proof on a schedule and after significant events (an update, a restart), and MUST surface a regression — the download client's egress IP now matching the host, or imports now copying instead of linking — as a health failure with a remedy, rather than waiting for the next manual doctor run.
```

### Rationale & alternatives

```text
Verification-as-monitoring is the natural extension of the project's "prove it, don't assume it" ethos. The alternative — trusting the one-time setup proof indefinitely — is exactly the silent-regression failure the tool exists to catch.
```
